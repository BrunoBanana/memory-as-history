# Memory as History：工程可靠性推进计划

日期：2026-09-17。基线提交：`2c96697`（1.1.0）；本轮补丁版本：`1.1.1`（待发布）。后续事务工作见 [1.2 首批实现计划](2026-09-17-transaction-integrity.md)。
本轮目标：修复可复现的协议与状态缺陷，建立持续回归检查，并明确下一版本的验收条件。

## 本轮结论

原有 114 个单元测试、6 项可靠性检查和两个机制演示脚本均通过，
但它们没有通过 MCP 调用服务器工具，也未覆盖部分跨模块状态组合。
新增 14 个回归用例后，确认并修复以下七类问题。

| 问题 | 触发方式与影响 | 修复及回归证据 |
| --- | --- | --- |
| MCP 返回值类型错误 | `flag_sensitive` 已提交数据库变更，却对字典再调用 `to_dict()`，向客户端报执行失败 | 直接返回存储层结果；真实 stdio 测试检查敏感标记、解除锚定及后续拒绝重新锚定 |
| MCP 输入错误不一致 | `remember` / `narrate` 的非法输入抛出未处理异常，客户端缺少自纠错信息 | 沿用现有结构化错误格式，补充 tier 提示；4 个协议用例检查错误和无意外写入 |
| 空白来源降低佐证门槛 | `source=""` 或纯空白被当作已知来源，单个佐证即可锚定敏感记忆 | 与 `None` 一样视为未知；3 个用例验证重复来源不计数、两个不同来源可通过 |
| 遗忘记忆可获得隐藏锚点 | 先遗忘再 `pin()` 仍成功，恢复后未经新的锚定决策便出现锚点 | 在写入前拒绝；检查无隐藏锚点、无成功审计条目，恢复后仍须显式锚定 |
| 多任务经典圈重复召回 | 同一记忆被纳入两个 scope，占用两个召回名额，挤掉其他记忆 | 按 memory ID 去重后分配预算；保留所有 scope 记录，代表条目为最早仍活跃的记录 |
| 冲突记录绕过遗忘 | 建立冲突后遗忘其中一条，该内容仍随 `recall().conflicts` 返回 | 召回只返回双方均未遗忘的开放冲突；历史可查，恢复后冲突重新出现；覆盖双方分别被遗忘 |
| 首次召回的复核状态矛盾 | 一条过期解释在主体中为 current，在待复核区又为 stale | 先刷新复核状态，再构造各返回区；覆盖普通记忆与锚点 |

实现位于 `src/memory_as_history/storage.py` 和 `server.py`；
回归用例位于 `tests/test_reliability_regressions.py`、`tests/test_server.py`。
所有新增回归均先在未修复实现上确认失败，再逐项修复并验证。

## 版本安排

### 1.1.1：收敛本轮修复

以补丁版本交付上述修复。保持数据库 schema 不变、已有工具参数不变；
`list_conflicts()` 增加 `forgotten_at_a` / `forgotten_at_b` 字段供历史检查。
多 scope 的完整成员关系继续通过 `list_canon()` 获取。
本补丁修正后续操作的约束，不自动清理旧库中可能已存在的异常锚点或来源分级；
历史数据的审计与修复策略需在下一阶段单独定义。

发布前验收：

1. 本轮 128 个测试和可靠性脚本保持通过，三个 MCP 兼容性作业与 OS/Python 作业全绿。
2. wheel/sdist 构建成功，干净环境可安装 wheel 并运行协议回归。
3. 审查差异并创建对应发布记录。包版本已更新为 1.1.1；正式发布前，修复保留在 CHANGELOG 的 Unreleased。

### 1.2：事务完整性与来源语义

下表是下一阶段的工作计划。除明确列出的当前行为外，并发和故障影响尚需专门复现；
现有多进程测试只证明独立写入数量正确，不能作为所有状态转换具有原子性的证据。

| 优先级 | 工作 | 验收条件 |
| --- | --- | --- |
| P1 | 用两个独立 Store/进程和可控同步点测试共享状态转换；检查 `narrate`、`canonize`、`mark_conflict`、`pin/forget` 的读后写竞争 | 并发叙事最多一个 current，版本链完整；活跃 scope/冲突不重复；遗忘状态与锚点约束不能相互越过 |
| P1 | 验证业务写入与审计写入的事务边界，注入中途写入失败并设计统一回滚 | 失败调用不留下可被下一调用意外提交的部分写入；成功变更有对应审计；`pin_denied` 的预期拒绝日志仍保留 |
| P1 | 明确 archive→testimony 与锚定门槛的关系 | 当前 `corroborate()` 首次调用即升级，包括同源重复；下一版需统一“独立佐证”的定义，并明确已有 testimony 数据如何解释或迁移 |
| P1 | 审查 `unpin()` 的审计契约 | 当前解除锚定没有理由参数，也不写入审计；明确兼容策略，确保以后能够解释锚点为何移除 |
| P2 | 确定敏感来源检查在 canon 和 narrative 路径上的边界 | 当前独立佐证要求约束 pin，不能声称覆盖全部召回路径；用相同输入测试各路径，并决定采用阻止、显式标注还是其他策略 |
| P2 | 明确记忆遗忘后已有叙事的处理方式 | 当前叙事是独立保存的文本，引用某条记忆不使其随遗忘自动改写；定义过期标记/复核流程，保留历史可追溯性 |
| P2 | 将检索的人工检查变为数值与排序回归 | 覆盖 BM25 公式、中文/英文混合分词、空查询、旧 token 缓存、查询性能和排序；明确单字、停用词和零相关结果的约定 |
| P2 | 将机制演示转为有断言的可重复评价 | 至少把 usefulness 演示变成失败时返回非零的测试；区分“机制约束成立”和“LLM 实际选择调用工具”的评价结果 |

推荐从两个 P1 事务工作项开始：先提交能稳定暴露问题的测试，再决定事务实现。
来源语义和叙事传播涉及协议约定，应另写短设计说明，避免在补丁里隐式改变历史数据含义。

## 本地复现

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -e ".[test]"
python -m pytest tests/ -q
python reliability_test.py
python usefulness_test.py
python poisoning_test.py
```

兼容性验证应在不同虚拟环境分别安装 `mcp==1.2.0`、`mcp>=1.2,<2`、`mcp>=2,<3`，
然后运行同一套测试；不依赖真实用户记忆库或外部模型 API。
